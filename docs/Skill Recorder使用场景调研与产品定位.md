# Skill Recorder 使用场景调研与产品定位

调研日期：2026 年 10 月 17 日  
调研目的：结合 IrisGo 与微软 Skill Recorder，明确本项目适合服务哪些人、哪些工作，以及如何描述和验证使用场景。  
调研范围：IrisGo 公开资料、微软开源仓库 README / 生成指令 / 评估场景、本项目 README / 产品方案 / 部分生成代码。未安装实测 IrisGo，未运行上游评估或真实业务流程。

> 本文是面向场景梳理的综合报告。IrisGo 的完整资料与证据边界见 [IrisGo 产品调研报告](IrisGo产品调研报告.md)。本文的场景优先级和产品建议属于调研判断，不代表已验证的用户需求，也不修改现有项目范围。

## 1. 先明确我们要帮助用户完成什么

**建议将当前 Skill Recorder 定位为：把业务人员已经会做、但难以完整说清的工作，通过一次示范、必要澄清和人工确认，整理成 Agent 可以复用的 Skill。**

用户最核心的诉求可以写成：

> 我已经会做这项工作，但每次教 AI 都要重新解释很多细节。我想按平时的方法做一遍，让系统提炼出流程，问清必要规则，形成下次处理新材料时可以使用的技能。

这里包含三个不同的成功节点：

| 成功节点 | 用户得到什么 | 对当前项目的意义 |
| --- | --- | --- |
| 流程被说清楚 | 目标、操作、筛选规则、输入输出与例外得到确认 | 判断系统是否理解了示范 |
| Skill 被交付 | 生成可审核、可导出的技能，标明适用条件和能力依赖 | 当前阶段的主要交付目标 |
| 工作被代办 | 执行 Agent 在新输入上完成任务，必要时定时运行 | 后续执行与验证环节，不能由导出成功代替 |

本项目方案将当前阶段收敛到审核和导出 Skill；生成数据结构也明确使用 `executionVerified: false`，渲染时提示“尚未进行业务试运行”。因此，使用场景需要同时描述用户最终想完成的工作，以及本期交付到哪里。[L2][L3]

## 2. 两个调研对象分别带来了什么启发

### 2.1 IrisGo：理解用户为何愿意教 AI

IrisGo 强调 Watch & Learn、个人上下文、持久技能与后台执行，希望用户通过带教获得长期代办能力。其独立工作者方案集中在每日简报、邮件分类、会议总结和费用报告。[I1][I2]

对本项目的启发是：

- 用户购买的是减少重复解释、整理和操作的负担；录制只是达成这一价值的方式。
- 适合示范的任务往往包含默认做法，例如看哪个字段、先查什么、遇到什么情况跳过。
- 场景要从一项具体工作开始，例如“把符合条件的询价邮件整理成线索表”，避免直接用“办公自动化”这样宽泛的名称。
- 长期价值需要后续执行结果来证明，“教一次、永远运行”不能成为当前生成阶段的效果承诺。

### 2.2 微软 Skill Recorder：明确录制如何变成技能

上游 README 给出的核心链路是：录制实际工作 → 重建意图和步骤 → 用户审核 → 生成 Skill 或 Automation。[M1]

生成指令进一步明确了几个重要原则：[M2][M3]

1. **一次录制是一个例子。** 应从意图提炼可复用流程，区分必要规则与偶然细节。
2. **保留业务目标，允许改变操作方式。** 用户在网页上操作 GitHub，生成的技能可以改用 `gh` CLI；录制不是对未来点击轨迹的约束。
3. **区分固定配置和每次变化的输入。** 稳定仓库地址可以成为配置，某次订单号、日期和临时文件名通常不能直接固化。
4. **生成计划可由用户修正。** 模型提出泛化方式、固定值、工具和步骤，用户确认后才生成。
5. **自动化的触发条件需要额外确认。** 单次录制通常不包含“以后何时执行”的信息，上游要求将推测的运行时间写成待审阅的假设。

上游评估覆盖网页到表格、发票提取、调研汇编、报销、销售线索入 CRM、发布说明、GitHub Issue 分类等。它们是合成素材和生成结果评估，不是真实客户成功案例，也不能证明业务执行已经可靠。[M4][M5]

### 2.3 对当前项目的定位建议

| 维度 | IrisGo 的公开主张 | 微软 Skill Recorder 的设计 | 本项目建议聚焦 |
| --- | --- | --- | --- |
| 核心价值 | 持续代办，减少日常管理负担 | 将一次真实操作泛化成技能或自动化定义 | 把隐含业务经验整理成可信的技能 |
| 用户角色 | 带教并委托 AI 的工作者 | 示范、审核和修正流程的技能作者 | 熟悉业务流程、已有或准备使用 Agent 的人员 |
| 主要交付 | 跨应用工作结果与后台服务 | Skill / Automation 产物 | 确认后的流程、规则和导出 Skill |
| 关键难点 | 长期自主执行的可靠性 | 泛化、参数提取和工具映射 | 证据不足、业务规则澄清、目标环境能力匹配 |
| 效果验证 | 是否长期节省时间 | 生成结果是否符合预期流程与工具约束 | 内容正确性先验收，实际执行效果后续单独验证 |

**建议借鉴 IrisGo 对用户价值的表述，采用 Skill Recorder 更明确的创作与交付边界。**

## 3. 什么样的工作值得录制

适合优先研究的任务，应当同时满足以下条件：

| 条件 | 用户身上的具体表现 | 为什么重要 |
| --- | --- | --- |
| 有复用机会 | 每周重复，或每次有一批同类对象 | 带教成本可以被后续复用摊薄 |
| 示范信息量高 | 涉及多个页面、文件或应用，文字说明容易漏步骤 | 录制能比简短提示词多提供有效信息 |
| 有稳定规则 | 筛选、匹配、分类和格式标准大部分可说清 | 系统才能从单次案例形成适用范围 |
| 输入会变化 | 日期、客户、订单、项目或文件每次不同 | 可以明确检验是否真正泛化 |
| 结果可检查 | 有字段、清单、报告模板或完成条件 | 用户能判断系统理解得对不对 |
| 存在执行路径 | 目标 Agent 有相应文件工具、API、CLI 或浏览器能力 | 技能有机会交付后被实际使用 |

不宜作为首批重点的任务包括：一句话足以描述的简单整理、没有复用需求的一次性工作、主要依赖不可解释判断的决策，以及目标 Agent 完全无法访问所需系统的流程。后一类仍可能有流程沉淀价值，但不能仅凭录屏就认定可以自动执行。

频率也不是唯一标准：低频但复杂、容易遗忘且需要交接的流程，也可能值得记录；其价值更偏向经验传递与规范化。

## 4. 使用场景应沿着三种需求展开

### 4.1 教给自己的 Agent

用户经常做同一类任务，已经在使用 Agent，但通用提示词不足以表达个人流程。示范后形成自己的技能，下次在新输入上调用。

代表场景：固定口径周报、竞品信息整理、发票登记、发布说明生成。

### 4.2 将单个示例扩展到同类对象

用户会处理一条记录，希望将筛选、匹配、填写和检查规则扩展到一批记录。

代表场景：订单登记、客户线索处理、账单核对、Issue 初筛。

这里必须确认集合范围。用户演示三条记录，并不自动意味着以后处理全部记录；“全部符合条件”“用户指定列表”“仅当前选中项”需要区分。上游强调从少量样本推广到 N 个对象，本项目应通过业务澄清确定这个 N 的边界。

### 4.3 把专家经验交给其他人或团队 Agent

熟练人员展示流程，将隐含口径和例外处理整理出来，供同事学习或其他 Agent 使用。

代表场景：新人入职操作、月末核对流程、特定内部系统操作、团队发布准备流程。

这类场景需要确认谁编写、谁审核、谁执行，以及接收方是否拥有相同工具和权限。当前可研究 Skill 的可移交性；SOP 独立导出在现有方案中属于规划分支，不应直接当作现成功能宣传。[L2]

持续自动代办是上述技能的后续使用方式，还需要调度、运行时输入发现、异常处理和授权机制。本期不宜把它与录制生成混成同一个完成标准。

## 5. 候选场景地图

下表是基于公开场景和项目方向整理的候选，不是已验证的市场排序。优先级综合考虑示范价值、结果可检查性和对当前生成范围的适配度。

| 优先级 | 用户与触发时刻 | 具体工作 | 录制能补充的信息 | 适合形成的产物 | 依据 |
| --- | --- | --- | --- | --- | --- |
| P0 | 运营/项目负责人准备周报 | 从业务系统取数，按固定口径筛选并形成报告 | 数据源、口径、关联键、模板和核对步骤 | 按周期与项目参数运行的周报 Skill | IrisGo 报告场景与本项目方向推导 |
| P0 | 销售/运营收到一批询价邮件 | 提取客户需求，匹配客户资料，登记线索 | 有效线索标准、重复判断、字段映射 | 邮件到线索表或 CRM 的 Skill | 上游 lead-to-crm 场景改写 |
| P0 | 财务/行政整理周期性账单 | 将票据与流水匹配，归类并输出差异 | 匹配规则、容差、异常分流、输出字段 | 对账或费用报告准备 Skill | 上游 invoice-extract / expense-report；IrisGo 费用报告 |
| P1 | 产品/采购定期更新资料 | 查询多个网站，记录价格或规格变化 | 口径、币种、来源优先级、更新时间 | 竞品或供应商信息整理 Skill | 上游 web-to-spreadsheet / research-compile |
| P1 | 研发负责人准备版本说明 | 收集合并 PR，分类整理变更与检查项 | 仓库、范围、分类和排除条件 | 发布准备 Skill | 上游 release-notes；建议先以文稿为交付 |
| P1 | 项目维护者清理 Issue | 筛选问题、识别缺失信息并提出处理意见 | 分类依据、重复判断、处理范围 | Issue 初筛 Skill | 上游 github-issue-triage |
| P1 | 业务专家带教新人 | 演示复杂内部流程并说明例外 | 隐含步骤、决策理由、交接条件 | 可交接的 Skill；SOP 为规划方向 | 本报告推导 |
| P2 | 独立工作者每天开始办公 | 综合邮件、日历、待办生成优先事项 | 个性化优先级与跨源关联方式 | 简报 Skill，长期运行需另接执行端 | IrisGo Daily Brief & Radar |

若首批用户以研发人员为主，可将“发布准备”提前。它有现成 `gh` / `git` 工具，便于检验“网页示范转为原生工具执行计划”的价值；优先级应随真实用户群调整。

## 6. 三个适合深入梳理的场景卡

### 场景 A：把每周报表制作方法教给 Agent

**用户与时刻：** 运营或项目负责人，每周固定汇总业务进展。用户已经有模板和数据口径，制作时需要多次切换系统与表格。

**用户原话：**“每周都是按这套口径做周报。我做一遍，你帮我整理成以后换个时间范围就能用的技能。”

**一次示范：** 打开数据源 → 选择时间和项目 → 导出或读取数据 → 排除不计入记录 → 按关联字段合并 → 计算指标 → 填入模板 → 核对合计。

**必须问清：** 统计周期与时区、纳入/排除标准、重复记录处理、缺失数据处理、指标公式、报告接收对象是否属于本次技能范围。

**每次变化：** 起止日期、项目、输入文件或当前数据。固定口径和模板只在用户确认后固化。

**本期交付：** 周报 Skill，包含输入、公式、数据来源、模板和核对条件；数据访问工具与账号要求明确列出。向他人发送报告若纳入目标，需要单独描述动作与未来执行条件。

**验收：** 生成内容能说明如何处理另一周数据；不会固定本次文件名或日期；总量与分类明细的核对逻辑明确。后续用另一周期试跑，才能评价实际结果是否正确。

### 场景 B：把邮件中的客户需求转成标准线索记录

**用户与时刻：** 销售运营或独立经营者，在处理新询价邮件时逐条查询客户资料并登记线索。

**用户原话：**“这类询价我都要查客户、提取需求、填到表里。我示范两封，你帮我归纳规则。”

**一次示范：** 搜索候选邮件 → 判断是否为有效询价 → 提取公司与需求 → 查询客户资料 → 检查是否已登记 → 创建或更新记录。

**必须问清：** 处理哪些邮件、同一线程如何去重、客户匹配键是什么、老客户的新需求如何处理、字段缺失时保留空值还是追问、是否包含回复邮件。

**每次变化：** 邮件范围、客户、需求、已有登记状态。演示中的客户邮箱和公司名称属于样本数据。

**本期交付：** 邮件到线索记录的 Skill。未来执行端需要邮箱读取、客户查询及表格或 CRM 写入能力；录制器能读邮箱，不代表目标 Agent 已具备所有这些能力。

**验收：** 新客户、新需求、重复邮件、信息缺失四种情况均有明确处理规则；不能把模型推测的客户资料写成已确认事实；是否回复客户需要在技能范围中明确。

### 场景 C：把票据核对经验转成可复用规则

**用户与时刻：** 财务或行政人员，集中整理一段时间内的票据和付款流水。

**用户原话：**“我知道怎样把这些票据和流水对起来，但规则写起来很繁琐。看我处理几个例子，再把匹配方法整理出来。”

**一次示范：** 读取流水 → 打开票据 → 按金额、日期和商户匹配 → 判断差异 → 归类 → 填写核对表 → 列出待处理项。

**必须问清：** 金额容差、跨日/跨币种规则、一对多与多对一匹配、重复票据、缺失凭证，以及哪些情况必须交给人处理。

**每次变化：** 账期、流水文件、票据集合、部门或项目。历史匹配结果不能固化成未来规则。

**本期交付：** 对账或费用报告准备 Skill。建议首批验证以核对表和异常清单为结果，再决定是否扩展到报销提交。

**验收：** 每项匹配能追溯到输入；不强行匹配不确定项；正常、缺失、重复、金额不一致均有处理方式。真实财务效果仍需新样本核验。

## 7. 一个场景如何从“录到了”走向“教明白了”

以邮件登记为例，录制时的事实与未来规则应这样区分：

| 录到的事实 | 仍需确认的问题 | 确认后进入 Skill 的内容 |
| --- | --- | --- |
| 用户打开了列表第一封邮件 | 是处理第一封，还是所有未处理询价？ | 明确集合范围与筛选条件 |
| 用户复制某个客户邮箱 | 该邮箱是固定联系人，还是本次客户信息？ | 作为当前输入提取或运行时查询 |
| 用户跳过一封邮件 | 因为重复、无效，还是暂缓？ | 写明跳过条件与处置方式 |
| 用户进入客户系统查询公司 | 依据哪个字段匹配，多个结果如何选择？ | 查询步骤、匹配键与歧义处理 |
| 用户点击保存 | 保存是否成功，如何识别重复？ | 写入后的结果检查与去重规则 |
| 用户当天上午演示 | 以后是否每天运行？ | 默认不推定调度；另行确认触发方式 |

这也是当前项目“深度分析”的产品价值：把操作证据、必要查询和用户回答组织成可以审核的业务流程。具体补证能力是否可用应按当前实现逐项核验，设计文档不能替代上线证明。[L2][L4]

用户旅程可收敛为：

```mermaid
flowchart LR
    A[选择一项值得复用的工作] --> B[示范代表性案例]
    B --> C[核对实际操作]
    C --> D[补齐规则和必要证据]
    D --> E[确认泛化后的流程]
    E --> F[生成并导出 Skill]
    F -. 后续执行与验证 .-> G[目标 Agent 处理新输入]
```

一次示范能够展示正常路径，但没有出现的异常分支需要补充说明；不能要求模型从一个成功案例中完整猜出业务制度。

## 8. 后续梳理场景可直接使用的模板

每个场景建议填写以下内容，再讨论页面和功能：

| 字段 | 要回答的问题 |
| --- | --- |
| 场景名称 | 用“动作 + 对象 + 结果”命名，例如“汇总询价邮件并登记客户线索” |
| 发起人 / 审核人 / 使用者 | 谁示范，谁确认规则，谁以后使用技能？ |
| 发生时刻 | 什么事件让用户需要这项工作？多久发生一次、每次多少条？ |
| 当前方法与成本 | 涉及哪些应用，耗时多久，最容易漏哪一步？ |
| 为什么需要录制 | 哪些信息靠简短文字难以描述？ |
| 一次示范范围 | 从哪里开始，到哪个结果结束？哪些属于无关操作？ |
| 业务规则 | 筛选、匹配、计算、分类、例外分别是什么？ |
| 固定配置与变化输入 | 哪些稳定，哪些每次由用户提供或重新查询？ |
| 产物与成功条件 | 输出什么，如何检查正确、完整且符合预期？ |
| 生成端条件 | 录制与分析需要什么材料，哪些信息需要补证？ |
| 执行端条件 | 接收技能的 Agent 有哪些工具、账号和资源权限？ |
| 本期边界 | 本次交付流程、Skill、SOP 还是执行结果？ |
| 验证材料 | 是否能提供下一批不同输入、预期结果和异常案例？ |

访谈时，优先请用户展示“最近一次真实处理过程”，再问哪些地方每次相同、哪些变化。只询问“你想自动化什么”容易得到过于宽泛的回答。

## 9. 建议的验证顺序和判断标准

建议先招募少量真实流程拥有者，分别验证报表制作、邮件登记和票据核对三个方向；这是建议的研究方案，本次尚未开展用户访谈或业务测试。

每个用户提供一段代表性示范、一组不同输入和至少一个例外。先验证是否能低成本产出正确技能，再在获得授权且具备条件的执行环境中验证新输入。

| 阶段 | 优先观察的指标 | 能回答的问题 |
| --- | --- | --- |
| 场景筛选 | 重复频率、手工耗时、描述困难点、现有替代方法 | 录制是否比直接写提示词或已有脚本更有价值？ |
| 流程提炼 | 漏步骤数量、关键规则覆盖、澄清和修改时间 | 系统是否真正减少了整理经验的负担？ |
| Skill 交付 | 样本值误固化、依赖遗漏、未决项显式程度 | 产物是否足够清楚，能交给目标 Agent？ |
| 后续执行 | 新输入完成率、人工介入、异常恢复成本 | 是否具备复用价值？ |
| 持续使用 | 复用次数、维护时间、净节省时间 | 带教投入是否值得？ |

净收益可以按“多次手工处理原需时间 − 首次带教与审核时间 − 后续执行、复核及维护时间”估算。模型运行时间与用户实际投入时间应分开记录，不设未经验证的节省比例。

**本次调研建议优先验证的命题是：业务人员能否通过示范与少量澄清，比自己编写完整指令更省力地交付一个可复用 Skill。** 如果这个命题成立，再扩展团队交接、技能维护和持续自动化，会有更清楚的依据。
