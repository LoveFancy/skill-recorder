（120 秒）

这里有两道鸿沟。第一道是真实操作到规则：演示告诉我们这一次发生了什么，但一次具体操作，并不自动构成下一次也适用的规则。打开列表第一封邮件，是只处理第一封，还是处理所有未处理的？复制了某个邮箱，是长期配置，还是本次客户信息？这些都需要补证、澄清和审核，不能让模型自行猜测。

第二道是规则到可重复执行：即使规则提炼正确，也不代表实际能反复执行成功。目标环境有没有语义匹配的工具？权限和依赖是否满足？换一批输入、遇到例外、隔一段时间再运行，结果还对不对？这些要靠能力映射和执行验证来回答。

比如“回复所有未处理的客户邮件”，可以是一条正确的规则。但如果工具只能新建邮件，不能保留回复线程，它就无法正确执行这条规则。即使找到了支持回复的工具，还需要验证不同邮件、附件和异常情况下的结果。找到工具是一层，执行效果过关又是一层。

先看三类输入。第一是语音，我们已经内置了语音模型，用户边操作边讲，系统能够录下讲解并转成文字。第二是屏幕，我们基于关键帧变化检测自动截图，把操作过程中的画面变化记录下来。第三是浏览器，我们已经实现了浏览器插件，能够采集点击等真实交互事件，补充仅靠屏幕画面看不到的操作信息。

再看分析。我们已经引入 Claude Code Agent，用它分析这些录制采集的原始数据。在这层基础上，深度分析已经部分实现，包括已有的补证、澄清和审核能力；其中自动补证还需要进一步实测复核，不能说整个深度分析已经成熟。

最后是产物。转为标准制品也已经部分实现，已经具备 Skill 等产物的生成与导出基础。Skill 的验证相对充分；SOP 和使用手册已有首版，但尚未发布，内容质量也还没有经过真实业务检验。

外部实践提供了补充佐证：本项目基于微软开源的 skill-recorder 做派生扩展，已有可复核的工程基线；IrisGo 也已把 Watch & Learn 做成产品推向市场。这些说明这一方向有现实的工程与产品基础，但不等于本课题的所有技术问题都已解决。

但这里必须分清楚：我们现在有的是 Demo，还不是一个可以交给大家日常使用的产品。 核心模块做出来，只是说明有了继续验证的基础；用户能不能放心使用 Skill Recorder，最终看的是效果。

参考 Muse 产品经理在采访中分享的经历：他们几周就做出了 Demo，但到正式发布，又经历了七个多月的打磨。这个案例提醒我们，做出可展示的原型，与把它打磨成可用产品之间，还有大量细致的工作。

对我们来说，这些工作具体落在四个问题上：能不能去掉录制里的无关噪音，又不误删关键动作？能不能正确还原跨窗口、跨系统的操作轨迹？能不能生成保留真实规则、没有把样本值写死的 Skill？换一批输入、隔一段时间再执行，它还能不能重复完成任务？

这四个环节都需要更精细的打磨和评测。当前受控业务 MCP 的自动调用链路尚未接通，也尚未开展真实业务试运行，重复执行的可靠性仍是后续必须验证的目标。 我们不能用一次 Demo 成功，代替产品效果的验证。

高频追问速查

（不上屏，备于演讲者视图）

| 质问 | 一句话回答 |

| --- | --- |

| 这不就是 RPA 吗？ | ①RPA 学路径，本方案学规则；②RPA 回放点击，本方案翻译成对既有 MCP/CLI/接口的调用，浏览器只是兜底 |

| 和 Computer Use 有什么区别？ | Computer Use 每次现场看屏、现场点，什么也不沉淀，结果每次不可预期、事后难复核；本方案沉淀的是带证据的规则，执行落在接口层 |

| 录下来的点击凭什么稳定跑？ | 我们不回放点击。 执行路径到公司既有能力里重选，产物标明每步载体与稳定性等级 |

| 浏览器兜底不还是脆弱？ | 承认脆弱，所以是第三优先级且必须显式标注。关键是比例【待补】；高频兜底会被反馈为能力建设需求 |

| 公司没那么多 MCP 怎么办？ | ①没有也能用，只是更多步骤走兜底；②SOP/手册完全不依赖能力快照；③会沉淀一份带频次的能力缺口清单，反过来指导建设优先级 |

| 怎么保证映射等价？ | 必须保留账号、线程归属、附件、数据范围与授权语义；不许凭名字相似认定等价；判不了的交人 |

| 中台已经写了通用 Skill，为什么还要演示？ | 不是写得不好，通用、精炼、稳定正是它的优点；但通用不等于适配每个营业部、每位一线员工，口径与例外的差异只有当事人知道。二次加工的诉求很强，而要改什么只有"会做但不会写"的人知道——演示正是让他把这一公里交出来的通道 |

| 为什么不培训业务人员写 Prompt？ | ①描述工作仍有遗漏、失真与整理成本；②一线人员还需学习指令与 Skill 编写方法 |

| SOP 自动保鲜是不是夸大？ | 保鲜是机制必然结果（记录随操作产生），但独立文档导出未发布、版本与变更提示未实现 |

| 录屏不就是隐私黑洞？ | 本机处理、端侧转写、端侧敏感扫描、只读业务访问、发送前显式确认 |

| 一次演示就能学会？ | 明确否认。 一次演示只提供一个样例，必须叠加自动补证与一次澄清；本期只验收知识产出质量 |

| 效果有数据吗？ | 评测分数 + 实测净收益口径；尚未开展真实业务试跑 |

| Demo 已经做出来，为什么还不能交付使用？ | 核心模块初步构建不等于产品效果过关；去噪、轨迹还原、Skill 生成与新输入下的重复执行仍需精细打磨，当前尚未开展真实业务试运行 |

| 这不就是个人效率工具？ | 模型是可买的公共品，企业自己的工作方式买不到 |

| 只解决生成够吗？ | 坦率承认不够，给出七环节完整图景；这套演进有软件工程范式作参照 |
