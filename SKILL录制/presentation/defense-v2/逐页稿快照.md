## P3 · 卡点有两层：供给主体 · 转化通道

**一句话**：问题是亲身撞上的，而且有两层——不是一层。

**上屏**

- 眉标：问题的本质
- 顶部一行（发现过程，**不配图、不展开**）：两个独立渠道互相印证 —— ① 我自己写 Skill、整理 SOP：**做这件事只要【待补】，写清楚却花了【待补】**；② 推广 workmate：一线员工是业务专家，却**不知道怎么把工作转成大模型能操作的 MCP / Skill**。
- 主体（左右分屏）：

**左 · 层一：工作知识与 AI 能力长在不同的人身上**

|               | 一线业务人员 | 熟悉 AI 的人 |
| ------------- | ------ | -------- |
| 工作知识与判断口径   | **具备** | 缺少      |
| 写成可执行指令的能力 | 缺少    | **具备** |
| 被重复工作消耗的程度 | **严重** | 较轻      |

两句（第二句红框）：
① 找人"翻译"会二次损耗，更关键是**不可规模化**——懂 AI 的人覆盖不了成千上万项日常工作。
② **集中编写也不行，但不是因为写得不好。** 专业人员产出的通用 Skill 通用、精炼、稳定，**却不必然适配每个营业部、每位一线员工**——口径、例外、本地惯例的差异只有当事人知道。**现实中对通用 Skill 二次加工的诉求非常强烈，而要改什么，恰恰只有那个"会做但不会写"的人才知道。** 

**右 · 层二：转化通道的三重损耗**

| 遗漏 | 下意识的默认动作写不出来 |
| --- | --- |
| **失真** | 回忆是重构，不是记录 |
| **成本** | 写清楚常常比做一遍更慢 |

- 底栏（可引用的定义）：人类工作知识中存在大量**隐性成分**，可被执行但难被完整言说。把"言说"作为唯一输入通道，**既筛掉了最需要帮助的使用者，又系统性丢失了难以言说的那部分知识**。

**配图**：层二配一个漏斗——输入"真实工作"，经"言说"这道窄口，输出被削掉三块。

**讲稿**（120 秒）

> 这个问题不是从文献里读到的，是从两个完全不同的方向同时撞上来的。一个来自我自己：我要把【待补：具体工作】交给 Agent，动手写 Skill、顺手沉淀 SOP，结果时间全花在回忆先看哪个字段、逐步截图、把跳跃的操作写成线性步骤，还有返工——我不是不会做，我是说不清。另一个来自一线员工：他们对业务极其专业，口径、例外、为什么这么判断都答得上，但卡在一个本不该由他们解决的问题上。两个渠道互相印证，说明这不是个人体感，是一类普遍卡点。
> 上升为问题定义有两层。层一是谁来教：最值得交给 AI 的工作恰恰集中在一线业务人员手上，而现实解法是找懂 AI 的人一对一翻译，这个人数量有限，根本覆盖不过来。
> **这里我要特别澄清一句，免得被理解成"专业人员提炼得不好"——恰恰相反。** 由专业人员集中编写的通用 Skill，本来就是通用的、精炼的、稳定的，这是它的优点。但问题是：它是否一定完全适配每一个营业部、每一位一线员工？**并不一定。** 口径的细微差别、哪些情况属于例外、本地长期形成的处理惯例——这些只有当事人自己知道。**所以现在大家对通用 Skill 做二次加工的诉求非常强烈**，而最后这一公里要改什么，恰恰只有那个"会做但不会写"的人才知道。于是又绕回同一个卡点。
> 所以瓶颈既不在模型，也不在业务能力，更不在中台写得好不好，而在于**我们要求业务人员先掌握一项他本不需要掌握的技能**。
> 层二是怎么教：即便换一个很会表达的人来写，描述通道本身仍有三重结构性损耗。所以"培训业务人员写 Prompt"能提升下限，解决不了这一层。
> 工作越跨系统、步骤越多，描述中的遗漏与衔接损耗越明显。这也是我们优先选择跨系统、多步骤工作的原因。

**来源**：§1.1、§1.2

## P4 · 让工作本身，成为输入

**一句话**：核心主张——换的是输入通道（说 → 做），不是换用户的技能。

**上屏**

- 眉标：核心主张
- 主标题：**让工作本身，成为输入**
- 副标题：以真实操作承载业务知识，降低人向 AI 传授工作方法的成本。
- 主体（左右两列对照卡）：

|      | 今天 · 描述式输入        | 本课题 · 演示式输入           |
| ---- | ----------------- | --------------------- |
| 用户要做 | 写出完整无歧义的指令，自备截图样例 | **按平时的方法做一遍**，再回答几个问题 |
| 能力门槛 | 流程表达能力 + AI 使用经验  | **只需会做这项工作本身**        |
| 信息来源 | 事后回忆的重构 + 人工挑选素材  | 当场发生的真实操作证据，时序完整      |


> **措辞纪律**：本页标题必须与封面同一套说法。"从会写指令到会做工作"只是主张在门槛侧面的推论，**不得当作主张本身**。

**配图**：两条通道示意——左：人 → 文字 → AI，标出遗漏 / 失真 / 成本；右：**真实实操 → 同步录制 → AI 分析**。用浏览器操作、带 REC 标识的屏幕录制、Agent 三个图标区分；下方分别标注“照常完成业务”“屏幕 · 语音 · 事件”“还原步骤、提炼规则”。强调操作与录制同步进行，随后由 AI 分析素材。图下说明：**边做边录，让操作过程成为 AI 的输入。**

**讲稿**（90 秒）

> 针对前面两层卡点，我们的主张就是——**让工作本身，成为输入。** 人最擅长的是做，不是说；让他按平时的方法做一遍，系统再帮助提炼，关键判断由人澄清和审核。
> 它同时回答三个被忽略的问题。谁来教——最需要 AI 帮忙的是一线业务人员，但把工作翻译成 AI 指令需要 AI 使用经验，这两种能力几乎不在同一个人身上。用什么教——跨系统的复杂工作，拿截图加文字拼凑着喂，既费力又讲不全。
> 第三条最关键，我开场就讲、不等被问：**演示只是输入方式，不是执行方式。** 系统不回放用户的点击，而是把演示出来的业务目标，翻译成对公司内既有 MCP、业务接口和内部 CLI 的稳定调用。这句话就是本课题与 RPA、与各类录屏回放产品的分界线。

**来源**：§0

## P5 · 技术锚点：真实操作 ≠ 规则 ≠ 可重复执行

**一句话**：从一次演示走向可重复执行，要跨过两道鸿沟：**把真实操作提炼成正确规则，再让规则在真实环境中可靠执行。** 录到了，不等于理解对了；规则写对了，也不等于以后能反复做对。

**上屏**

- 眉标：核心技术问题 · 两道鸿沟
- 主标题（大字）：**真实操作 ≠ 规则 ≠ 可重复执行**
- 副标题：**一次做对，不能替代换输入后的反复验证。**
- 主体（三段两道鸿沟图；每段一个问题，每道鸿沟一行机制）：

| 真实操作 | 规则 | 可重复执行 |
| --- | --- | --- |
| **这一次，实际做了什么？** | **换个样本，应该怎么做？** | **换批输入，还能持续做对吗？** |

  第一段 → 第二段：**补证 + 澄清 + 审核**——区分样本与配置，补齐范围、条件与例外。
  第二段 → 第三段：**能力映射 + 执行验证**——核实工具、权限与依赖，在新输入、多轮运行中检验效果。


**配图**：三段横排，段间各画一道断裂，分别标“知识提炼”和“执行落地”。“真实操作”用事件流，“规则”用带证据与边界的文档，“可重复执行”用多组输入与循环执行图标。两段箭头均标需要完成的工作，不画成无条件自动贯通；第三段使用虚线边框，注明“待验证”。上方的三列表仅为配图文案，不再叠加四问表。

**讲稿**（120 秒）

> 这里有两道鸿沟。第一道是**真实操作到规则**：演示告诉我们这一次发生了什么，但一次具体操作，并不自动构成下一次也适用的规则。打开列表第一封邮件，是只处理第一封，还是处理所有未处理的？复制了某个邮箱，是长期配置，还是本次客户信息？这些都需要补证、澄清和审核，不能让模型自行猜测。
>
> 第二道是**规则到可重复执行**：即使规则提炼正确，也不代表实际能反复执行成功。目标环境有没有语义匹配的工具？权限和依赖是否满足？换一批输入、遇到例外、隔一段时间再运行，结果还对不对？这些要靠能力映射和执行验证来回答。
>
> 比如“回复所有未处理的客户邮件”，可以是一条正确的规则。但如果工具只能新建邮件，不能保留回复线程，它就无法正确执行这条规则。即使找到了支持回复的工具，还需要验证不同邮件、附件和异常情况下的结果。**找到工具是一层，执行效果过关又是一层。**
>
> 所以我们不能把“录到了”“生成了 Skill”“已经能重复执行”当成同一件事。现有的描述、检索、录制或界面操作能力各解决一部分问题，但从真实操作到可信规则、再到可靠执行，需要把这些环节连起来，并分别验证。
>
> 当前课题聚焦的是前一道鸿沟，以及为后续执行准备有证据、有边界的知识和能力映射设计。执行设计页会展开执行方式翻译；可行性页会说明当前 Demo 做到哪里。**重复执行可靠性仍是后续必须验证的目标，不是当前已经兑现的效果。**

**四个事实样例（不上屏，追问时展开）**

| 录到的事实 | 必须确认的问题 |
| --- | --- |
| 打开了列表第一封邮件 | 处理第一封，还是所有未处理的？ |
| 复制了某个邮箱地址 | 固定配置，还是本次输入？ |
| 跳过了一条记录 | 重复、无效，还是暂缓？ |
| 在周一上午演示 | 不代表以后每周一上午自动运行；触发条件须另行确认 |

> **表述口径**：“≠”表达的是“不能自动推出 / 不代表已经实现”。真实操作、规则、可重复执行分别对应记录、知识与效果三个层次，不能用某一层完成代替下一层验收。生成阶段可以声明、检查部分工具与依赖条件，但真实执行可靠性仍需后续试运行验证。

**来源**：§1.6、§1.7、§2.3 机制五；2026-10-20 补充的产品化效果要求与“两道鸿沟”判断。

> 讲完问题，这一页回答我们到底要做一件什么事。整张图从左到右就是全部。
> **左边是输入。** 我们希望录制发生在员工真实工作的现场，也就是他日常办公的云桌面里——不是让他专门找个环境演示一遍，而是他照常工作。录的东西有五类：随操作变化自动抓取的屏幕截图、鼠标点击与窗口切换、浏览器里的真实点击事件、语音口述，以及剪贴板和终端输出。**为什么要这么多源？** 因为光看屏幕录像，不知道他复制了什么、执行了什么命令；而**语音口述是捕获"为什么这样判断"成本最低的通道**——这恰恰是文字 SOP 里最缺、也最该写清的那部分。

> - **云桌面内的部署与性能表现属于落地事项**，【待补：以实际验证结论为准】——本页讲的是目标部署形态，不要讲成已完成验证；

## P9 · 关键机制：把操作翻译成能力调用

**一句话**：把跨系统实操转为明确的能力调用路径，同时固化业务规则与参数来源。

**版式**：双泳道。左泳道是真实操作（登录业务系统 → 下载报表 → 用 Excel 加工数据 → 加工后数据发到邮箱），右泳道是翻译后的动作（调用业务系统 MCP → 编写数据处理逻辑 → 调用邮箱 MCP 发送），左右按行对应；登录与下载两步合并对应一次「调用业务系统 MCP」。三方对比见 P10。

**上屏**

- 眉标：执行方式翻译
- 主标题：**关键机制：把操作翻译成能力调用**
- 副标题：**演示是需求说明书，不是执行脚本。**
- 案例：**生成并发送月度经营报告**（方案示意）。

| 左泳道 · 真实操作 | 右泳道 · 翻译后的动作 |
| --- | --- |
| 01 登录业务系统（输入账号，进入系统）<br>02 下载报表（按周期筛选，导出 Excel） | **调用业务系统 MCP**：一次调用完成登录会话与报表取数，替掉界面上的两步 |
| 03 用 Excel 加工数据（公式、透视表、异常剔除） | **编写数据处理逻辑**：把 Excel 里的加工步骤写成可复用的处理逻辑 |
| 04 加工后的数据发到邮箱（填写收件人，附上文件） | **调用邮箱 MCP 发送**：收件人与附件由任务传入，发送结果可回读 |

- 底栏：人做一步，Skill 里就有一步对应；参数（周期、范围、收件人）由任务传入，换一批输入仍走同一条路径。

**配图**：左列四个带序号的浅灰步骤卡，右列三个浅蓝能力卡，之间用箭头连接；第一张能力卡跨两行，表示一次调用合并了登录与下载两步。

**讲稿**（180 秒）

> 用一个完整任务说明：员工先从 A 业务系统下载某个月的数据，按本岗位的自定义规则分析，形成报告，再通过邮件发送。录制保留的是这些操作，转换后的工作流则需要明确每一步调用什么能力、输入来自哪里、输出交给谁。
>
> 第一步，A 系统的查询和下载映射为业务 MCP，周期与业务范围作为本次任务的参数。第二步，自定义规则封装为或复用一个具体的“月度经营分析 Skill”，负责指标汇总、变化分析、异常标记及报告生成。这里的规则只是案例示意，真实口径和规则版本需要业务人员确认。第三步，将生成的报告作为附件，调用邮箱 MCP 发送。
>
> 收件人邮箱也是变量，要从前序工作或本次任务提供的业务上下文中找到。不能把录制时用过的地址写成固定值。整个工作流要明确变量来源：查询输出传给分析 Skill，分析产出的报告传给邮箱 MCP，收件人从已确认的前序结果中取值。
>
> 稳定的调用路径还需要明确能力标识与规则版本、输入输出约定和执行顺序。每一步检查结果后才继续：数据缺失、分析失败或收件人来源不明时，应停在当前步骤处理，而不是猜测参数继续发送。确认的规则可用确定性计算和模板实现，并通过新数据、多轮运行及失败场景验证，不能将“生成了路径”直接等同于“路径已可靠”。
>
> 工具选择仍按既有设计：原生工具、CLI 或已开放接口优先，再复用已授权业务 MCP；缺少匹配能力的 UI 专属步骤才使用浏览器兜底。这里的 A 系统 MCP、分析 Skill 和邮箱 MCP 是方案中的角色名称，实际工具是否具备所需语义必须核验。
>
> 底部对比的是执行通道：录制回放沿界面路径运行，Computer Use 在执行时看屏决策，本方案优先把业务目标编排为明确的能力路径。并不是说 RPA 不能使用变量，或 Computer Use 只能单独工作。

> **实现口径**：本页为执行方案。受控业务 MCP 自动调用链路与版本化依赖声明尚未实施，分析 Skill 的封装和工作流的稳定性需按实际进度验证；不能作为已跑通能力展示。P12 继续说明当前 Demo 进展。

**来源**：§2.3 机制五、§2.5；用户补充的跨系统分析报告案例

## P10 · 对比：不是 RPA 回放，也不是 Computer Use

**一句话**：三种执行方式的差别不在“能不能自动”，而在“按什么执行”。

**上屏**

- 眉标：方案定位
- 主标题：**不是 RPA 回放，也不是 Computer Use**
- 副标题：三种执行方式的差别，不在能不能自动，而在按什么执行。
- 主体（三栏对照，本方案高亮）：

|  | RPA 录制回放 | Computer Use | 本方案 |
| --- | --- | --- | --- |
| **执行依据** | 录下来的点击、输入与坐标 | 每一步实时识别界面 | 用户操作对齐到既有能力 |
| **换一批输入** | 页面或流程一变就要重录 | 每次重新判断，慢且不稳 | 只换参数，路径不变 |
| **出问题时** | 只能整段重跑，难定位 | 结果难复现，难审核 | 逐步校验，能定位到哪一步 |
| **适合场景** | 界面与步骤都固定的重复操作 | 界面多变、系统不开放时的临时任务 | 跨系统、多步骤、需要反复执行的日常工作 |

- 底栏：与 RPA 的分界线：**不回放点击，而是调用能力。**

**配图**：三张对照卡，本方案一张用浅蓝底与主色顶边强调；不画界面截图。

**讲稿**（约 60 秒）

> 有人会问：这不就是 RPA 吗？不是。RPA 录的是界面路径，页面或流程一变就得重录；Computer Use 是每一步看屏幕临时决策，慢，而且结果不容易复现。我们做的是把一次真实操作翻译成明确的能力路径——同一套路径换一批输入还能跑，出错时能定位到具体哪一步。

## P11 · 同源三产出，应用场景决定形态

**一句话**：同一份工作知识，可以支持人按流程执行、Agent 调用能力，以及新人学习和查阅功能。

**版式**：三张卡片统一说明“用途、场景、本例产物”，底部一条收束带；不设截图区（本页不放实物证据）。

**上屏**

- 眉标：产物设计
- 主标题：**同源三产出，应用场景决定形态**
- 同源说明：同一份已审核的工作知识——**登录取数 → 下载报表 → Excel 加工 → 邮件发送**（与 P9 案例同为月度报表）。

| | SOP · 人来执行 | Skill · Agent 执行 | 使用手册 · 人来学习 |
| --- | --- | --- | --- |
| 用途 | 规范操作步骤与业务判断口径 | 编排工具与分析 Skill，复用调用路径 | 说明功能入口、参数与操作方法 |
| 场景 | 岗位交接、人工操作、复核 | 周期报告、重复任务自动化 | 新人培训、操作查询、使用答疑 |
| 本例产物 | **月度报表编制 SOP**：登录业务系统、下载报表、用 Excel 加工数据、把结果发到邮箱，逐步写清判断与例外 | **月度报表 Skill**：调用业务系统 MCP 取数 → 执行数据处理逻辑 → 调用邮箱 MCP 发送，参数随任务传入 | **月度报告数据说明手册**：按功能讲清登录、筛选下载、加工口径与邮件发送，便于学习与查阅 |

- 底栏（收束）：同一份知识，三种形态：**人照着做、Agent 跑起来、新人看得懂。**


**讲稿**（90 秒）

> 同一个“登录业务系统、下载报表、用 Excel 加工数据、把结果发到邮箱”的案例，应用场景不同，产物组织方式也不同。
>
> SOP 服务人的实际工作，按任务顺序写清登录哪个系统、筛选什么周期、如何导出、怎样应用业务规则、如何复核报告和发送邮件，适合岗位交接、日常操作与人工复核。它保留真实操作。
>
> Skill 服务 Agent 重复完成任务。本例产物是“月度报表 Skill”，编排业务系统 MCP 取数、数据处理逻辑和邮箱 MCP 发送，明确每步输入输出与参数来源。分析 Skill 承载已确认的自定义规则，工作流 Skill 负责把取数、分析成稿和发送衔接起来，适合周期报告和重复任务的自动化。
>
> 使用手册服务培训与按需查阅，按功能说明筛选器在哪里、参数是什么意思、数据怎样导出、报告怎样生成、附件怎样发送。它帮助新人学会使用系统，不要求读者从头到尾执行整项任务。
>
> 三类产物共用已经审核的事实、规则和适用边界，只有 Skill 需要把界面操作翻译为能力调用。SOP 与使用手册也有独立价值，不以 Agent 已经执行成功为前提。

> **实现口径**：SOP 与使用手册首版已实现、尚未发布，内容质量未经真实业务验证；跨系统工作流与分析 Skill 的编排属于本页案例设计，不代表当前已可稳定重复运行。生成后仍需查看正文并显式保存。

> 这一页先回答一个具体问题：我们的 Demo，现在到底已经做到了什么？结论是，**核心能力已经初步构建，采集和初步分析已有基础，后面的深度分析与制品生成正在完善。**

> 对我们来说，这些工作具体落在四个问题上：**能不能去掉录制里的无关噪音，又不误删关键动作？能不能正确还原跨窗口、跨系统的操作轨迹？能不能生成保留真实规则、没有把样本值写死的 Skill？换一批输入、隔一段时间再执行，它还能不能重复完成任务？**

## P13 · 大处着眼，小处着手

**一句话**：只做生成，但说清生成在整张图里的位置。

> 前面说明了 Demo 已具备的基础，以及距离可用产品还有哪些效果关卡。未来规划分三层：先把个人工作的知识产出质量与复用效果验证好，再探索团队共享、交接和口径统一，最后才是企业级的发布、权限与质量治理。
>
> 模型与 Agent 能力逐渐普及之后，企业仍需要沉淀自己的工作方式：业务判断口径、处理惯例、跨系统衔接，以及各类例外。这些知识从个人经验变成可交接的流程资产，才可能为团队与组织复用。
>
> L2 虽有部分设计，但组织级使用效果尚未验证；L3 是长期方向。这是本课题希望逐步走向的价值，而非当前 Demo 已经兑现的成果。

## 高频追问速查（不上屏，备于演讲者视图）

| 质问 | 一句话回答 |
| --- | --- |
| 这不就是 RPA 吗？ | ①RPA 学路径，本方案学规则；②**RPA 回放点击，本方案翻译成对既有 MCP/CLI/接口的调用**，浏览器只是兜底 |
| 和 Computer Use 有什么区别？ | Computer Use 每次现场看屏、现场点，**什么也不沉淀**，结果每次不可预期、事后难复核；本方案沉淀的是带证据的规则，执行落在接口层 |
| 录下来的点击凭什么稳定跑？ | **我们不回放点击。** 执行路径到公司既有能力里重选，产物标明每步载体与稳定性等级 |
| 浏览器兜底不还是脆弱？ | 承认脆弱，所以是第三优先级且必须显式标注。关键是**比例**【待补】；高频兜底会被反馈为能力建设需求 |
| 公司没那么多 MCP 怎么办？ | ①没有也能用，只是更多步骤走兜底；②SOP/手册完全不依赖能力快照；③会沉淀一份**带频次的能力缺口清单**，反过来指导建设优先级 |
| 怎么保证映射等价？ | 必须保留账号、线程归属、附件、数据范围与授权语义；**不许凭名字相似认定等价**；判不了的交人 |
| 中台已经写了通用 Skill，为什么还要演示？ | **不是写得不好，通用、精炼、稳定正是它的优点**；但通用不等于适配每个营业部、每位一线员工，口径与例外的差异只有当事人知道。**二次加工的诉求很强，而要改什么只有"会做但不会写"的人知道**——演示正是让他把这一公里交出来的通道 |
| 为什么不培训业务人员写 Prompt？ | ①描述工作仍有遗漏、失真与整理成本；②一线人员还需学习指令与 Skill 编写方法 |
| SOP 自动保鲜是不是夸大？ | 保鲜是机制必然结果（记录随操作产生），但**独立文档导出未发布、版本与变更提示未实现** |
| 录屏不就是隐私黑洞？ | 本机处理、端侧转写、端侧敏感扫描、只读业务访问、发送前显式确认 |
| 一次演示就能学会？ | **明确否认。** 一次演示只提供一个样例，必须叠加自动补证与一次澄清；本期只验收知识产出质量 |
| 效果有数据吗？ | 评测分数 + 实测净收益口径；**尚未开展真实业务试跑** |
| Demo 已经做出来，为什么还不能交付使用？ | **核心模块初步构建不等于产品效果过关**；去噪、轨迹还原、Skill 生成与新输入下的重复执行仍需精细打磨，当前尚未开展真实业务试运行 |
| 这不就是个人效率工具？ | 模型是可买的公共品，**企业自己的工作方式买不到** |
| 只解决生成够吗？ | 坦率承认不够，给出七环节完整图景；这套演进有软件工程范式作参照 |
